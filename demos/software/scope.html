BEFORE THE FIRST PATCH

One bug. One agreed result.

A useful repair request tells us how to make the defect happen and how to recognize a fix. Start with a sanitized description; repository access and an agreement come after the initial review.

A request we can assess

  1. Observed behavior: the exact input and wrong output, or the visible steps that trigger the bug.
  2. Expected behavior: one concrete outcome, including types, ordering or formatting where relevant.
  3. Environment: framework/runtime versions, browser if relevant, and the command used to reproduce.
  4. Constraints: which behavior must stay the same, and any deadline or dependency that affects scope.

Omit passwords, API keys, customer records and private production logs. A fictional example is usually enough for the first conversation.

Example: a stale search result

This is a fictional request, not client work.

Observed: Search for “oak”, then “pine”. If oak finishes last,
the screen replaces the pine results with oak results.
Expected: Only the newest search may update the screen.
Reproduce: Render the search component; resolve the second request
first, then the first. The final results must still be pine.
Constraints: Preserve loading and error behavior. React/TypeScript.
Scope question: Does this also affect cancellation or unmounting?

Issues and attachments are public: do not include confidential code, credentials, personal information or customer records. No booking, payment or response time is guaranteed.

For an initial public inquiry, share only a short sanitized summary and fictional reproduction steps. Keep your full plain-text brief and private source locally until a private channel and repository access are agreed. Do not attach an executable source archive to an initial inquiry. If your mail service refuses an archive, use an authorized repository or release-download link instead; do not rename files to bypass the mail service's rules.

Agree access before sharing private source. Keep private repositories and customer material private. A handoff should identify the exact commit or release, include the commands and expected results for the agreed check, and explain how to verify any downloaded package.
