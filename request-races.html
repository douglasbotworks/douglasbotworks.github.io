When an old
request wins.

A search result can be correct for the previous query and still be wrong for the screen. Here is a small, reproducible example of that failure.

THE FAILURE ORDER

  1. 01 Start request A
  2. 02 Start request B
  3. 03 B finishes with the current result
  4. 04 A finishes and overwrites B

The last response is not always the current response.

MAKE IT DETERMINISTIC

Control completion order.

A useful regression check does not wait for a slow network to happen. Give the component two controlled promises. Resolve B first and A second. The expected screen still shows B. Repeat with A rejecting: an obsolete failure should not replace B's result.

Also leave B pending while A resolves. The screen should remain loading for B. A fix that handles only two completed successes can miss this case.

THE BOUNDED CHANGE

Let the active effect commit.

In the linked React example, effect cleanup marks the old effect inactive and aborts its controller. Success and failure callbacks check whether their effect remains active before updating state. That guard still matters when a custom loader ignores cancellation.

Cleanup runs when the query or loader changes and on unmount. The example also checks React development effect cleanup, replacement loaders and synchronous loader failures. This pattern belongs to the component's effect lifetime; shared caches and other request owners need their own agreed semantics.

READ THE ACTUAL RESULT

Seven failures become eleven passes.

The published fictional report contains eleven cases: seven fail before the repair and all eleven pass afterward. Current success and error handling remain covered alongside the stale-result checks.

Read the machine-readable report. Its environment is React 18.3.1 development rendering with jsdom and controlled injected promises in Node. It does not establish native browser, network, layout, customer-code or production integration acceptance.

For a separate state-machine example, inspect the request-state demonstration. Its contract also covers duplicate completion and canceled requests; it is a different example, not an extra claim about the React component.
